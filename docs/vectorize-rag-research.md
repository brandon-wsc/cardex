# Term discovery eval / Vectorize research — not an approved product contract

## Starting point

The public contract is a facts backend, not an answer generator: `resolve_alias` maps known words to references; `lookup_rates` and `score_candidates` query D1 with explicit filters; rate and term records carry provenance and effective windows. Embedding search is currently out of scope, so shipping it would require a PRD change and an architectural decision. The existing D1 dataset is the agreed reference corpus for this retrieval eval; [STATUS](STATUS.md) still describes its facts as synthetic, so retrieval performance is not evidence of issuer-term accuracy. Sources: [PRD §§3–5, 11](PRD.md), [ADR 0001](adr/0001-product-shape.md), [ADR 0002](adr/0002-maintenance-surface.md), [ADR 0003](adr/0003-facts-language.md), [query implementation](../packages/mcp-worker/src/query.ts).

## Agreed question and scope

**Term discovery first.** Ask whether semantic retrieval helps a Caller find a relevant D1 Term when it does not know the Term ID. Unknown Alias / Tag / Card discovery is a possible later experiment, not part of the first eval. Search may discover references; it must not infer eligibility, whitelist membership, numeric Rates, fee amounts, expiry, or a best Card. A retrieved Term does not prove that a spend satisfies it, and search must never clear an `unknown_exclusions` entry. Exact IDs and existing structured filters remain the direct path. Sources: [PRD §§2–5](PRD.md), [ADR 0001](adr/0001-product-shape.md), [ADR 0003](adr/0003-facts-language.md).

The new capability is **semantic Term discovery**; the Caller may use the retrieved D1 facts as context for generation, making its end-to-end flow RAG. Cardex itself remains a facts backend, not a text generator. Cloudflare's RAG reference architecture explicitly queries Vectorize for IDs and looks up original documents in D1 before generation. Sources: [Cloudflare RAG reference architecture](https://developers.cloudflare.com/reference-architecture/diagrams/ai/ai-rag/), [Vector database overview](https://developers.cloudflare.com/vectorize/reference/what-is-a-vector-database/).

## Eval first: question, data and comparison

Pin a local D1 fixture/snapshot and a small human-labeled set of realistic Caller questions, including Cantonese/English paraphrases, queries with Card context, queries without it, multiple relevant Terms, expired Terms, and cases with **no** relevant Term. Label relevant Term IDs and the query's `as_of` independently of the retrieval outputs. Keep test questions separate from text used to build the index; avoid treating paraphrases generated from the Term text alone as evidence of real-world performance. Do not publish this dataset as issuer facts.

Compare (a) a reproducible **lexical Term search baseline over the same D1 corpus** (a new offline eval baseline, not an existing public tool) and (b) semantic candidate retrieval over the same corpus. Keep existing direct ID / structured tools as a separate known-ID control path, not a competing unknown-ID search baseline. Existing `resolve_alias` is a baseline for a later Alias experiment, **not** a Term-search baseline: it does not search Term text. Report recall@5 for relevant Term IDs, misses of important Terms, incorrect candidates on no-match queries, response latency and cost separately; do not collapse these into one accuracy number. Check stale/deleted/expired-pointer behavior separately from relevance. The acceptance threshold, dataset size, and whether to ship are **unsettled** until the eval is reviewed. Sources for existing tools and windows: [PRD §§3–5](PRD.md), [query implementation](../packages/mcp-worker/src/query.ts).

**Trigger:** run `python3 scripts/term_search_eval.py` on demand for the lexical baseline; run `python3 scripts/term_search_eval.py --provider ollama` with a local `ollama serve` and `ollama pull bge-m3:567m-fp16` to include local semantic retrieval. Cloudflare is a separate, billable opt-in: set `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN` privately and add `--semantic` (the default semantic provider remains Cloudflare). Neither mode runs automatically on PRs or a schedule. The script checks a pinned SHA-256 of `seed/seed.sql` against its labeled cases and reports corpus/query hashes and run date. A manually dispatched CI run may be added later if needed; no such trigger exists now. This concerns the *offline eval*, not any future production index synchronization after approved D1 changes. The 21 hand-authored cases (16 positive, five negative), including Cantonese (`yue`) and English slices, are exploratory, not representative production-query traffic; expand them before a ship decision. Both semantic arms use exact local cosine, **not Vectorize ANN**: they estimate relevance, but cannot measure Vectorize latency, indexing lag, approximate ranking or query cost. Embedding request/text/character counts are cost proxies, not measured Cloudflare billing.

## Candidate implementation to test, not yet selected

For the first experiment, index one D1 Term per vector with Card name, Term kind and a short operative excerpt; if a Term is long, split only at actual condition/section boundaries and retain its Term ID and segment number. Do **not** chunk by arbitrary token length across Rates, Cards or unrelated Terms, or embed full issuer PDFs as publishable facts: that would introduce unreviewed source material outside the propose→approve→apply loop. Issuer-source passages, if explored, belong on the maintainer's evidence-gathering side; human approval still precedes D1 publication. Rates, eligibility logic and effective dates always come from D1 at read time. Sources: [ADR 0002](adr/0002-maintenance-surface.md), [PRD §§3–5](PRD.md).

### Local model candidate: BGE-M3

Start with Ollama's `bge-m3:567m-fp16` for the optional local semantic arm. The [model author lists `yue` and `zh` in its training-language list](https://huggingface.co/BAAI/bge-m3/discussions/29), while explicitly warning that lower-resource languages may perform worse. Its [model card](https://huggingface.co/BAAI/bge-m3) specifies 1024-dimensional dense embeddings; [Ollama publishes an FP16 local build](https://ollama.com/library/bge-m3/tags) of about 1.2 GB. This fits [Vectorize's 1536-dimensional limit](https://developers.cloudflare.com/vectorize/platform/limits/), but local exact cosine is **not** a Vectorize test. The same BGE-M3 family is [available through Workers AI](https://developers.cloudflare.com/workers-ai/models/bge-m3/), though different serving implementations must not be presumed numerically identical.

The smaller [Qwen3-Embedding-0.6B](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B) is a possible second comparison: multilingual, 1024 dimensions, and a [639 MB Ollama build](https://ollama.com/library/qwen3-embedding:0.6b). Its model card recommends a special query instruction; an unprompted comparison would be unfair. Its general multilingual claim is not evidence of Cantonese retrieval quality. Neither model is a winner without held-out, naturally phrased Cantonese/English queries and negative cases.

### First local run (2026-11-15)

Using `python3 scripts/term_search_eval.py --provider ollama` on the 21 labeled questions and 46 pinned D1 Terms, Ollama `bge-m3:567m-fp16` (model digest `7907646426070047a77226ac3e684fbbe8410524f7b4a74d02837e43f2146bab`) returned 1024-dimensional vectors. Overall macro recall@5: lexical **0.84375**, local dense **0.9375**. For the 10 positive Cantonese (`yue`) questions: lexical **0.75**, dense **0.90**. For the five English positive questions both were **1.0**; the one formal Chinese positive question was also **1.0** for both. The two Cantonese and three English no-answer questions all returned at least one candidate under **both** methods (5/5 false hits by the current no-abstention metric); dense search missed both registered-Term IDs in the unscoped Cantonese registration question. Exact local cosine is a relevance proxy, not Vectorize ANN. This hand-authored sample is small and card-scoped for most questions; its apparent gain does **not** justify a production tool or a relevance threshold without independent queries and better negative handling. Per-case details are in the local ignored `scripts/out/term-search-local-bge-m3.json`; rerunning the command produces a fresh report.

### Additional unscoped stress cases (2026-11-15)

Run `python3 scripts/term_search_eval.py --provider ollama --cases scripts/term-search-eval-stress-cases.json`. This **separate** labeled set has 23 new questions, all without a `card_id`: 15 positives (13 colloquial Cantonese, two English) and eight no-answer negatives (seven Cantonese, one English). It covers unknown Card, expiry, annual-fee questions that belong to `card_fees` rather than Terms, and requests for personal account data that Cardex does not hold. Gold IDs are checked against the same pinned D1 seed and `as_of`; test coverage rejects duplicate IDs/queries shared with the initial set.

On this stress set, lexical recall@5 was **0.533** (Cantonese **0.462**), and local BGE-M3 dense recall@5 was **1.0** (Cantonese **1.0**). Lexical returned candidates for **3/8** no-answer cases; dense returned candidates for **8/8**. Both methods returned all candidates as unverified references; a dense nearest-neighbor match cannot establish that a Term exists for an unsupported request. These questions were hand-authored against the existing Term corpus by the same researcher, not sampled from real Caller traffic or independently blinded; this is a **targeted stress set, not an unbiased holdout**. Do not tune an abstention threshold on it and then report its score as generalization. Detailed local output: ignored `scripts/out/term-search-stress-local-bge-m3.json`.

## Potential Caller interface if eval justifies shipping

Keep current SQL-backed tools untouched: a Caller with known IDs or structured filters continues to use `get_term`, `lookup_rates`, and `score_candidates`. A proposed single `search_terms(query, as_of?, card_id?, limit?, detail?)` interface would discover Term IDs when the Caller does **not** know them. By default (`detail: "terms"`), Cardex fetches the matching D1 Terms and returns their facts, source and effective dates; `detail: "candidates"` returns only compact, D1-validated references and identifying information for optional follow-up with `get_term`. Neither mode settles applicability. The exact input/output shape and default window semantics remain to be specified in the PRD **if** the eval warrants the feature. A `sql` mode inside this new tool would duplicate the existing direct tools; `rag_only` would misleadingly suggest that vectors can be authoritative. Source for existing compact-result and follow-up convention: [PRD §§2–4](PRD.md).

1. Embed the query with the **same model** used for the index; search for a small set of candidate IDs. Cloudflare offers multilingual `@cf/baai/bge-m3`; its quality for Cantonese/HK issuer Terms must be measured rather than assumed. Sources: [Cloudflare bge-m3](https://developers.cloudflare.com/workers-ai/models/bge-m3/), [Vectorize query guide](https://developers.cloudflare.com/vectorize/best-practices/query-vectors/).
2. Use Vectorize as a **derived search index**: store opaque IDs and minimal routing metadata (`record_type`, optionally `card_id` / `kind`), not authoritative answer text. Even in candidate-only mode, verify existence and `as_of` against D1 before returning references; default mode hydrates facts from D1. Never use similarity score as factual confidence. Cloudflare supports metadata filtering, but filterable fields need metadata indexes; filters are applied before `topK`. Sources: [Cloudflare metadata filtering](https://developers.cloudflare.com/vectorize/reference/metadata-filtering/), [Cloudflare RAG architecture](https://developers.cloudflare.com/reference-architecture/diagrams/ai/ai-rag/), [PRD §§3–5](PRD.md).
3. After a proposal is approved/applied in D1, schedule an idempotent upsert/delete for affected index IDs; reconcile periodically against D1. Vectorize mutations are asynchronous and typically take a few seconds to become visible. A stale pointer must never return a deleted or expired fact; a miss cannot be treated as proof that no Term exists. This does **not** guarantee immediate discoverability of newly approved facts, so freshness requirements must be decided before launch. Sources: [Cloudflare Vectorize client API](https://developers.cloudflare.com/vectorize/reference/client-api/), [ADR 0002](adr/0002-maintenance-surface.md), [PRD §3.3](PRD.md).

## Practical limits and decision gate

Vectorize's current documented limits include 1,536 dimensions per vector, 64-byte vector IDs, 10 KiB metadata per vector, up to 10 indexed metadata fields, `topK` at most 50 when requesting metadata or values (100 without), and asynchronous upserts/deletes. Metadata is allowed to hold short text, but returning it as the answer would duplicate D1 truth. Sources: [Cloudflare Vectorize limits](https://developers.cloudflare.com/vectorize/platform/limits/), [client API](https://developers.cloudflare.com/vectorize/reference/client-api/).

## Delivery sequence

1. **Plan and eval on `chore/term-search-eval-plan`:** record the question and baselines here; follow with offline test data and a comparison harness on this branch if pursuing the eval. This branch does not change public tool behavior. The plan can be reviewed before the harness is added.
2. **Review results:** decide whether lexical search / better curated lookup data already solves the problem. The outcome may be **no Vectorize**.
3. **Only if warranted:** create a fresh `feat/term-search` branch from the then-current `dev`, update the PRD and add an ADR for the new contract before/with code, then implement, test and review the new read path. Avoid stacking a RAG PR on an unmerged eval PR; keep the dependency and decision visible. Sources for repo workflow: [execution conventions](EXECUTION.md), [PRD §11](PRD.md).

This is a proposed eval plan and possible interface, **not** a claimed performance result or an approval to add embedding search.

## Prototype implementation (2026-11-16, `feat/term-search`)

An experimental `search_terms` prototype landed on a feature branch per step 3 above — [ADR 0014](adr/0014-semantic-term-search.md) records the contract. Deliberate deviations/confirmations versus the sketch above:

- **Chunking is row-level:** one curated `terms` row = one vector (median 175 chars, max 486); the embedded document is `"card_name kind text"`, the same shape the eval used — contextual context from structured fields, not generated text. `merchant_list` terms stay one vector each despite enumerating merchants; a per-member fan-out is a documented later option.
- **Metadata is pointers only:** `card_id`, `kind`, `effective_from`, `effective_to`, `embed_hash`. `card_id` scope and the `as_of` window are enforced at **D1 hydration**, not trusted to index-side metadata filters — filters are a scale optimization the prototype does not configure.
- **Index sync is manual:** `scripts/term_search_index.py` reads D1 (`wrangler d1 execute`, local or remote; seed export is the fallback), embeds via local Ollama by default, and emits NDJSON for `wrangler vectorize upsert` plus a stale-id list via `--check-stale`. No apply-path hook — D1 writes never depend on the index.
- **Local dev degrades honestly:** Vectorize has no local binding mode and AI bindings always call remote (metered), so `wrangler dev` answers `search_unavailable` — the fail-closed path — rather than silently lexical-fallback. Tests inject `embed`/`queryIndex` fakes and never touch billable surfaces.
- **Known gap stands:** no similarity cutoff ships; the stress set's 8/8 no-answer false hits mean low-ranked hits may be noise. `similarity` is exposed only in `detail: "candidates"`.

*Update 2026-11-16:* index sync is no longer manual-only — [ADR 0015](adr/0015-term-index-sync.md) adds apply-time dirty marks in `decideProposal`'s batch plus a 15-minute `scheduled` reconcile (deletes via marks, inserts/updates via an `embed_hash` sweep). `term_search_index.py` remains the full-rebuild and stale-id `--check-stale` path.
